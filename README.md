# Агент управления тарифными маркетинговыми кампаниями

Кейс Beeline, хакатон HackAlem AI, трек «Телекоммуникации».

Агент решает, каким группам абонентов предложить смену тарифа, на какой тариф и через какой канал — при том, что истинная реакция аудитории заранее неизвестна и выясняется только платными пилотными кампаниями.

---

## Задача

Дана база из 23 441 абонента, 21 тариф и 4 канала связи. Нужно вернуть план из 1–10 кампаний, максимизирующий

```
net_arpu_gain = прирост ARPU по уникальным абонентам − затраты на все контакты
```

Главная сложность: выданная история смен тарифов описывает **другую** выборку абонентов. Узнать поведение целевой аудитории можно только пилотом — маленькой реальной кампанией, которая расходует общий бюджет и возвращает зашумлённую оценку.

Ресурсы общие для разведки и эксплуатации: 100 000 у.е., 15 000 контактов, 20 пилотов, 10 минут на прогон.

---

## Подход

Решение строится на трёх наблюдениях о структуре задачи.

### 1. Пространство гипотез сжимается до пар «ячейка → целевой тариф»

Истинный относительный эффект определяется тройкой `(current_tariff, arpu_segment, target_tariff)` и множителем канала. Признаки `data_segment` и `call_segment` на величину эффекта не влияют — они управляют только составом и ценностью аудитории.

Следствие: вместо перебора поведенческих признаков агент работает с **ячейками** `(current_tariff × arpu_segment)` — их 63, из них 21 имеет численность ≥ 200. Пилот, проведённый по ячейке целиком, переносится на все её допустимые подгруппы.

### 2. Ценность ячейки — не её размер

Крупнейшие по суммарному ARPU ячейки состоят из HIGH-абонентов на дорогих тарифах. Эффект в задаче **относительный**, а у такого абонента запаса для роста в процентах почти нет. Априорная оценка по истории показывает, что потенциал смещён в MID- и LOW-сегменты, где абонент может существенно увеличить счёт.

Поэтому очередь гипотез ранжируется по произведению `prior_theta × A_ячейки`, а не по `A_ячейки`. Первая волна разведки принудительно покрывает все три ARPU-сегмента — агент не должен потерять целый класс гипотез, если априор ошибся.

**Это гипотеза, а не факт о скрытой модели.** Ранжирование определяет только порядок проверки; итоговое решение принимается по результатам пилотов.

### 3. Порог обнаружения задаёт всю схему разведки

Шум пилота абсолютный и не зависит от канала: `SE = 0.804 / (m·√n)`, где `m` — множитель канала. Сигнал же масштабируется множителем. При решающем правиле «нижняя граница больше нуля» получаем:

| Разведка | SE | гипотеза проходит при mean > |
|---|---:|---:|
| 1 пилот × 200, SMS | 0.0875 | **0.144** |
| 2 пилота × 200, SMS | 0.0618 | 0.102 |
| 3 пилота × 200, SMS | 0.0505 | 0.083 |

Сильные гипотезы проходят с одного пилота. Слабые не окупают трёх. Отсюда стратегия — **широкий скан, а не глубокая проверка немногих**: около 14 гипотез по одному пилоту, оставшиеся пилоты — на добивание пограничных случаев.

Канал разведки — SMS. Один SMS-контакт несёт в `(0.65/0.50)² = 1.69` раза больше информации, чем push-контакт, при стоимости 4 у.е.; 20 пилотов по 200 — это потолок в 16 000 у.е., 16% бюджета. Push используется как запасной канал при нехватке денег. Call для разведки исключён: один замер на 200 человек стоил бы 32 000.

## Как агент принимает решение

```
1. Построить ячейки и априорную очередь гипотез (history + frozen_policy)
2. Первая волна: по одному пилоту × 200 через SMS на ~14 гипотез
3. Нормировать наблюдения и накопить оценки
4. Добивание: пилоты на гипотезы с mean > 0 > L, где A_ячейки × SE максимально
5. Отобрать гипотезы с L > 0
6. Построить кандидатов «сегмент × канал», отсечь убыточные
7. Жадно упаковать портфель в остатки бюджета и охвата
8. Вернуть 1–10 кампаний
```

### Оценка эффекта

Наблюдения одной гипотезы складываются взвешиванием по обратной дисперсии:

```
y_j    = observed_lift_ratio_j / m_j
v_j    = 0.804² / (n_j · m_j²)
mean   = Σ(y_j / v_j) / Σ(1 / v_j)
SE     = sqrt(1 / Σ(1 / v_j))
L      = mean − 1.645 · SE
```

В план попадают только гипотезы с `L > 0`. Нижняя граница здесь — прозрачный штраф за неуверенность, который не даёт масштабировать случайно удачный пилот. Это **не** одновременная 95%-гарантия для всего портфеля: адаптивный отбор и множественные сравнения её нарушают.

### Выбор канала

Для каналов с множителем ≤ 1 (`push`, `sms`, `digital_ads`) ожидаемый эффект равен `m · L`. Для `call` множитель 1.2 упирается в ограничение `min(conversion · m, 1.0)`, поэтому используется консервативная нижняя оценка `L`, а не `1.2 · L` — без знания конверсии отделить рост от насыщения невозможно.

Call при этом остаётся экономически оправданным: он выгоднее SMS при `theta × predicted_arpu > 284`, что выполняется на всех подтверждённых гипотезах с заметным эффектом. Бюджет позволяет 625 call-контактов, и они отдаются ячейкам с наибольшим `theta × средний ARPU`.

### Поправка на пилотные пересечения

ID абонентов, контактированных в пилоте, агенту недоступны — `run_pilot` возвращает только количество. Поэтому доход финальной кампании считается консервативно: если в ячейке `g` было `R_g` пилотных контактов, то для сегмента `S`

```
r        = min(R_g, |S|)
A_fresh  = sum_ARPU(S) − sum_top_r_ARPU(S)
gain_low = effect_low · A_fresh − |S| · cost_канала
```

Затраты списываются за весь сегмент. Это нижняя оценка, а не точная реконструкция дедупликации.

### Непересекаемость кампаний

Ячейка определяется парой `(current_tariff, arpu_segment)`, поэтому сегменты из разных ячеек не пересекаются по построению. Достаточно двух правил: **максимум один кандидат из каждой ячейки** и **один `current_tariff` на кампанию**. Отдельная проверка пересечений не требуется.

## LLM в контуре

Внутри зачётного прогона `act(env)` сетевых вызовов нет.

LLM работает **до сдачи**: получает агрегаты публичной истории и справочник тарифов, предлагает альтернативные целевые тарифы для ячеек и обоснования. Результат проходит валидацию схемы и замораживается в `frozen_policy.json`; его SHA-256 пишется в лог прогона. После заморозки `submission.csv` генерируется заново.

Это решает конфликт между использованием LLM и требованием воспроизводимости: `temperature=0` и «детерминированный оптимизатор после LLM» воспроизводимости не дают — разные допустимые предложения приводят к разным планам. Гарантию даёт только неизменный поставляемый артефакт.

Если политика отсутствует или повреждена, агент использует встроенный детерминированный порядок гипотез и помечает прогон флагом `policy_fallback`. Отсутствие LLM не меняет работоспособность.

## Структура репозитория

```
├── agent.py               точка входа: class Agent, act(env)
├── domain.py              ячейки, сегменты, очередь гипотез, чтение данных
├── estimates.py           нормировка пилотов, обратная дисперсия, границы
├── planner.py             кандидаты, поправка A_fresh, жадная упаковка
├── exploration.py         выбор следующего пилота, правило остановки
├── audit.py               JSONL-трассировка решений
├── frozen_policy.json     замороженный результат LLM-подготовки
├── tools/
│   ├── prepare_policy.py  предсдаточный LLM-вызов (необязателен)
│   └── selfcheck.py       проверка инвариантов и воспроизводимости
├── tests/                 тесты формул и механики
└── docs/
    ├── case_analysis.md   разбор механики кейса и скоринга
    └── strategy_spec.md   спецификация алгоритма
```

Вычислительное ядро — обычный локальный Python. Веб-сервисы, база данных и внешняя инфраструктура для контракта `act(env)` не нужны и не поднимаются.


## Трассировка решений

Каждый прогон пишет JSONL-лог, по которому восстанавливается любое решение агента:

| Событие | Содержание |
|---|---|
| `run_start` | seed, конфигурация, hash политики, стартовые остатки |
| `data_quality` | пропуски в данных, исключённые кандидаты с причинами |
| `arm_selected` | ячейка, целевой тариф, ранг, источник альтернативы |
| `pilot_result` | канал, запрошенный и фактический n, наблюдение, нормированные mean/SE/L |
| `explore_decision` | новая гипотеза / добивание / остановка и её причина |
| `candidate_evaluation` | фильтры, n, сумма ARPU, R_g, A_fresh, канал, gain_low |
| `plan_selected` | состав плана, стоимость, охват, суммарный gain_low |
| `run_end` | число пилотов, длительность, флаги, hash плана |

Для любой кампании из плана лог отвечает на вопросы: на каких пилотах она основана, какова оценка эффекта и её ошибка, почему выбран этот канал, сколько охвата засчитано консервативно и какой альтернативе не хватило бюджета или уверенности.

## Границы применимости

Раздел намеренно честный — эти ограничения стоит знать до того, как опираться на решение.

**Что гарантируется.** Соблюдение всех лимитов при корректном контракте среды; отсутствие пересечений между финальными кампаниями; отсутствие обрезки сегментов в штатном плане; воспроизводимость плана при одинаковых входах, политике, конфигурации и seed, если оба прогона прошли нормальную ветку без аварийной остановки по времени.

**Что не гарантируется.**

- Положительный `net_arpu_gain` при произвольных скрытых эффектах. Если в проверенных гипотезах нет ни одной с `L > 0`, контракт всё равно требует вернуть кампанию — агент возвращает push-сегмент с минимальным оценённым ущербом, и это минимизация потерь, а не обещание прибыли.
- Нахождение глобально лучшей пары «ячейка → тариф». Разведка ограничена 20 пилотами и работает по короткому списку гипотез.
- Глобальный оптимум упаковки портфеля. Используется жадная эвристика с несколькими весами, а не точное решение задачи о рюкзаке.
- Совпадение `submission.csv` при сравнении со средой, у которой **другая** скрытая модель эффектов. Один seed фиксирует выборку, но не эффекты.
- Формальная 95%-гарантия для портфеля целиком. Границы `mean ± z·SE` номинальные и поячеечные.

**Допущения.** Шум пилотов независим и нормален с указанной дисперсией; относительный эффект постоянен внутри ячейки; конверсия лежит в `[0, 1]`; структура ключей модели эффектов на судействе совпадает с выданной средой. Первые три следуют из кода среды, последнее — из того, что `environment.py` выдан участникам как контракт.

**Известные упрощения.** Поправка `A_fresh` консервативна: она может занулить оценку новой аудитории у маленькой ячейки после пилота и недооценить полезный повторный контакт. Если `pilot_history` на судействе всё же содержит ID, точный маргинальный расчёт — первое улучшение после базовой сдачи.
